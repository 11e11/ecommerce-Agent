# Specialist Runtime 工程改造

本次修改接入正式执行链路，没有新增模拟模型或模拟工具。测试中的固定响应仅用于可重复验证。

## 执行结构

外层仍是 DAG：确定性 Skill Router → Evidence Analyst → 各平台 Specialist 并行 → Manager → Reviewer。

Specialist 内部采用“有限规划 + 工具调用循环”：

1. Runtime 加载本平台证据、选中的 Skill、历史摘要和工具白名单。
2. 生成有限步骤的计划；代码验证步骤数、工具权限和证据缺口编号。
3. 每个取证步骤进入真实 provider 的 research 循环：模型决定是否调用工具及其参数，执行器校验权限、参数、平台和预算，通过 MCP 调用，将结果返回模型，由模型选择下一次调用或结束。
4. Runtime 保存工具结果的证据快照和工作记忆；反思检查步骤覆盖度。需要工具却没有成功观察的步骤不能被判为完成。
5. 最多重规划一次；到达工具次数或时间上限后停止取证，在最终报告中保留缺口。

这不是纯粹的自由 ReAct：外层仍是计划—执行—反思，内部 research 才是由工具反馈驱动的循环。

## 新增控制

- `agent_loop.AgentLoop`：管理 plan / act / reflect / final / stopped 状态迁移，调度前检查期限，持久化迁移、错误及停止事件。
- `assemble_context`：每次规划、反思和最终生成前，将 JSON 载荷控制在 48,000 字符内；优先缩短证据正文、检索结果和历史摘要，保留目标和 Skill 合同。提示模型正文是节选，不能由截断推断事实不存在；原始证据不修改。此数值不是 token 上限，也不包含独立传入的工具定义和系统指令。
- 工具参数按注册的 JSON Schema 校验，拒绝未知名称、额外字段和类型错误，并限制字符串长度与数量参数；非法请求也消耗预算。平台数据读取由执行器固定平台。
- trace 接口与详情页展示实际轨迹：可用工具、上下文预算、规划、调用、观察、反思、记忆和停止原因。
- 详情页补充要求通过既有 follow-ups 接口创建子运行，再执行完整 DAG。历史摘要仅作背景，不作为新证据引用。

## 可复述案例

“用户要求比较两个平台的标题规则。路由选中商品优化 Skill，各平台 Specialist 分别加载自己的证据和只读工具。模型先检索规则，再根据返回的章节编号决定是否阅读全文。执行器校验工具和参数，并保存结果供引用。如果检索失败，工作记忆保留缺口，不能直接当作任务完成。用户补充‘只列差异’时，系统创建关联上一轮的新运行，带入有限摘要，重新取证和审核。”

## 边界与运行

- 持久化轨迹与工作记忆快照用于检查和追踪；不支持从任意工具调用中途恢复进程。
- Manager / Reviewer 仍使用各自职责的结构化生成，不开放通用工具循环。
- 工具目前只读；这里没有新增自动写入电商平台的能力。
- 新执行合同改变后，管理员须重新发布默认协作图，旧图不静默迁移。
- 演示服务器仍使用原有 DemoSeedProvider。真实工具选择需使用正式运行入口并配置生成模型凭据；本次没有通过添加模拟响应来替代真实调用。

## 验证

针对上下文预算、状态迁移、到期拒绝调度、伪造工具、错误参数、跨平台隔离、空结果不算完成、多轮关联、报告和轨迹渲染进行自动化验证。
