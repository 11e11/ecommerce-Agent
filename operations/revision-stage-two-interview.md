# Baseline → 进阶方案：面试逐字稿

“最初系统接收用户的修改意见后，会把反馈和历史摘要带入新运行，再把两个平台都分析一遍。我发现两个问题：重新生成容易改动无关建议，而且即使最终保留了旧建议，也已经花钱重新分析了一次。

比如用户说：Amazon 不增加广告预算，只修改库存建议，Shopify 保持原样。我先补了结构化需求和修改范围控制，再根据这份范围决定执行哪些节点。

这里不是让模型判断缓存能不能用。模型负责理解修改要求，代码检查 Shopify 的输入报表、有效期、相关约束、Skill、模型和执行版本是否一致，以及旧结果有没有未验证的外部依赖。检查通过就复用 Shopify 的分析，只运行 Amazon Specialist；Manager 和 Reviewer 仍重新运行，更新汇总并审核。如果不能确认旧结果有效，就重新分析。

我用同一个案例的六种表达做真实模型对照。相对最初的文本反馈方案，修改范围检查从零条通过提升到六条通过，模型调用中位数从十次降到八次，输入 token 中位数减少约百分之十二。六次都能从日志确认 Shopify 没有重新调用。

代价是多了依赖检查和结果版本管理。耗时没有下降，因为之前两个平台并行运行，少算一个分支不一定缩短关键路径。当前验证的是给定报表下的反馈修订，动态工具上下文无法重验时仍然重跑。”

## 被追问时补充

**模型输出的修改要求是什么？**

```json
{
  "target_platform": "amazon",
  "categories": ["inventory"],
  "forbid_budget_increase": true,
  "preserve_platforms": ["shopify"]
}
```

Skill Router 仍是确定性能力匹配；反馈解释是单独的模型调用。预算限制与允许修改的类别分开，避免把“不增加广告预算”误解为“可以修改广告建议”。

**缓存具体怎么检查？**

“为每份平台分析保存依赖指纹和结果摘要，比较平台及共享输入、有效约束、Skill/Prompt/工具权限、模型与图版本；再检查证据时间和旧审核状态。有跨平台依赖、未知结果、旧工具调用或元数据缺失就重跑。部分证据不足的结果只在缺口不变时保留，不能借复用变成证据充分。”

**是不是恢复了 Shopify Agent 的运行？**

“复用的是已完成的结构化分析产物，不是从旧 Agent Loop 中间恢复。日志记录 task.reused 和来源运行，没有新 task.started。Reviewer 如果要求重做，仍会实际运行它。”

**相对于完整重跑的中间方案，收益多少？**

完整重跑为 11 次模型调用，进阶为 8 次，减少约 27.3%；输入 token 中位数减少约 22.2%。相对 baseline 的调用减少 20%、输入 token 减少约 12.4%。两组基准不同，不能混用百分比。

**能不能说响应更快？**

本次不能。baseline、完整重跑、进阶耗时中位数分别约 65.8、71.3、70.9 秒。进阶少做了总计算，但多了一次串行需求解释；原平台分支又是并行的，所以未证明延迟收益。

以上仅是单一场景、六种表达的结果；规则检查与模型语义评分分列，不说成普遍准确率。外部工具在本次反馈评测中统一禁用，不能声称工具调用也减少了。长期记忆尚未实施。
