# Baseline → 进阶方案：面试逐字稿

“最初系统接收用户的修改意见后，会把反馈和历史摘要带入新运行，再把两个平台都分析一遍。我发现两个问题：重新生成容易改动无关建议，而且即使最终保留了旧建议，也已经花钱重新分析了一次。

比如用户说：Amazon 不增加广告预算，只修改库存建议，Shopify 保持原样。我先补了结构化需求和修改范围控制，再根据这份范围决定执行哪些节点。

这里不是让模型判断缓存能不能用。模型负责理解修改要求，代码检查 Shopify 的输入报表、有效期、相关约束、Skill、模型和执行版本是否一致，以及旧结果有没有未验证的外部依赖。检查通过就复用 Shopify 的分析，只运行 Amazon Specialist；Manager 和 Reviewer 仍重新运行，更新汇总并审核。如果不能确认旧结果有效，就重新分析。

我用同一个案例的六种表达做真实模型对照。相对最初的文本反馈方案，修改范围检查从零条通过提升到六条通过，模型调用中位数从十次降到八次，输入 token 中位数减少约百分之十二。六次都能从日志确认 Shopify 没有重新调用。

代价是多了依赖检查和结果版本管理。耗时没有下降，因为之前两个平台并行运行，少算一个分支不一定缩短关键路径。当前验证的是给定报表下的反馈修订，动态工具上下文无法重验时仍然重跑。”

## 被追问时补充

**模型输出的修改要求是什么？**

```json
{
  "target_platform": "amazon",
  "categories": ["inventory"],
  "forbid_budget_increase": true,
  "preserve_platforms": ["shopify"]
}
```

Skill Router 仍是确定性能力匹配；反馈解释是单独的模型调用。预算限制与允许修改的类别分开，避免把“不增加广告预算”误解为“可以修改广告建议”。

**缓存具体怎么检查？**

“这些检查由代码完成，不再问一次模型。第一次分析完成后，把平台及共享报表、相关约束、Skill、提示词、工具权限、模型、图版本和证据缺口按固定顺序序列化，计算 SHA-256 指纹。第二轮用当前内容再算一次，和旧指纹比较；同时核对旧结果本身的哈希，防止结果被改动。

比如只修改 Amazon 库存要求，Shopify 的这些依赖没变，就继续检查：旧运行是否完成且审核通过，证据是否在有效期内，例如 Shopify 商品报表不能超过三天。旧分析如果依赖其他平台、调用过外部工具、引用了输入之外的证据，或者缺少校验信息，就重新分析。旧结果只是部分充分时，复用后仍保留原来的缺口，不会变成证据充分。”

对应代码：`ecommerce_ai_skills/runtime/reuse.py` 的 `dependencies()` 生成依赖指纹，`decide()` 执行比较与有效期检查。这里的结果哈希用于完整性校验，不是模型生成的文字摘要；比较的是本次输入快照，也不等于验证店铺实时数据没有变化。

**是不是恢复了 Shopify Agent 的运行？**

“复用的是已完成的结构化分析产物，不是从旧 Agent Loop 中间恢复。日志记录 task.reused 和来源运行，没有新 task.started。Reviewer 如果要求重做，仍会实际运行它。”

**相对于完整重跑的中间方案，收益多少？**

完整重跑为 11 次模型调用，进阶为 8 次，减少约 27.3%；输入 token 中位数减少约 22.2%。相对 baseline 的调用减少 20%、输入 token 减少约 12.4%。两组基准不同，不能混用百分比。

**能不能说响应更快？**

本次不能。baseline、完整重跑、进阶耗时中位数分别约 65.8、71.3、70.9 秒。进阶少做了总计算，但多了一次串行需求解释；原平台分支又是并行的，所以未证明延迟收益。

以上仅是单一场景、六种表达的结果；规则检查与模型语义评分分列，不说成普遍准确率。外部工具在本次反馈评测中统一禁用，不能声称工具调用也减少了。长期记忆尚未实施。

**禁用了什么工具？本次实际调用轨迹是什么？**

“本次评测专门验证修改范围和结果复用，所以把数据直接放进输入，把所有角色的工具白名单设为空、工具次数设为零。禁用的是知识检索、读取章节、查询约束，以及读取经营简报、指标、提案、证据等只读工具。没有允许 Agent 调用的外部工具，模型推理仍然真实执行。

实际轨迹是：模型解析反馈，Analyst 审计输入，代码检查依赖；Amazon Specialist 重新规划、分析输入、反思并输出，Shopify 直接复用已完成结果；随后协调节点、Manager、Reviewer 重新运行。日志里 Amazon 有启动事件，Shopify 有复用事件，没有任何工具调用事件。样例虽然有多条 act 阶段记录，但工具使用数为零，不能把这些阶段记录说成工具调用。”

禁用的八个工具：知识类 `opc.search_knowledge`、`opc.hybrid_search`、`opc.read_chapter`、`opc.get_constraints`；数据类 `opc.ops_briefing`、`opc.ops_metrics`、`opc.ops_proposals`、`opc.ops_evidence`。原本已经无工具权限的角色维持为空。Skill 路由、输入审计、指纹检查和范围合并由程序执行，不计为 Agent 外部工具调用；模型接口调用和独立评分调用也不是这八类工具调用。

配置见 `scripts/eval_revisions.py` 中对所有节点设置 `allowed_tools=[]`、`max_tool_calls=0`；真实轨迹见 `operations/revision-selective-eval/example-held-01-stage_two.json`，三组十八次正式运行的 `tool_calls` 均为零。因此这次只证明无外部工具条件下的修订与复用收益，没有验证带检索、动态取数的工具循环。
